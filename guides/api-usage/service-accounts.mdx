A service account is a Risk Cloud user built for automated integrations. Unlike a personal user
account, it has no interactive login, but it uses the same role-based permission structure as
regular users.

## Key benefits

- **Token interference prevention** — isolates integration credentials from personal user
  activity, so someone else regenerating their own token doesn't break your integration.
- **Lifecycle independence** — the integration keeps working even after an associated employee
  leaves the organization.
- **Third-party access control** — grant external vendors or consultants integration credentials
  without exposing any employee's personal account.

## Permission requirements

Service accounts follow the same permission model as standard users:

- API access permission must be explicitly enabled.
- Module entitlements apply (`BUILD`, `RECORDS`, `IMPORT`, etc).
- Application entitlements restrict data access.
- Step permission sets control Record visibility.

## Provisioning steps

1. Create the service account in the admin UI.
2. Enable API access permission.
3. Generate Client and Secret keys via the Access Key flow — see
   [Authentication](/guides/api-usage/authentication).
4. Create a dedicated Role named for the integration.
5. Assign the necessary module entitlements.
6. Configure Step Permission Sets for the relevant workflow stages.
7. Grant Application Entitlements scoped to the integration's needs.
8. Limit Build Access to integrations that actually modify workflow design.

## Common permission patterns

| Use case | Module | Application | Step Permission Set |
|---|---|---|---|
| Data warehouse reads | none | Read | Read |
| Record creation | `RECORDS` | Edit | Edit (origin step) |
| Bulk imports | `IMPORT` | Edit | Edit (origin step) |
| Audit exports | `STATUS` | Read | relevant sets |
| Workflow modifications | `BUILD` | Edit | Build Access required |

## Single vs. multiple accounts

- **Shared accounts** are simpler to provision but require coordinated token rotation and a
  retry-on-401 implementation across every dependent integration.
- **Individual accounts** isolate token lifecycles and let you tailor permissions per integration.

Default to **individual accounts** for production environments with multiple integrations across
different teams.

## Best practices

- Implement retry-once on `401` for shared accounts.
- Centralize token issuance to a shared secret store.
- Never generate production tokens from a developer's machine.
- Document account ownership for on-call reference.
- Scope permissions strictly to what the integration actually needs.
- Avoid granting `ADMIN` entitlements during development.
